# DevCleaner — правила работы для Codex и других агентов

## Назначение
DevCleaner — небольшая нативная macOS-утилита (Swift + SwiftUI, SwiftPM) для анализа места на диске и **выборочной**, контролируемой очистки кэшей разработчика.

## Главный принцип
Этот проект — одновременно рабочее приложение и учебный проект владельца. Приоритеты: **понятность кода → безопасность данных → минимальные изменения → функциональность → визуальная полировка**.

## Перед каждой задачей
1. Прочитай `AGENTS.md`, `ARCHITECTURE.md`, `ROADMAP.md` и задействованные Swift-файлы.
2. Сверь документацию с реальным кодом. **Реальный локальный код — источник истины**; документация может отставать.
3. Назови текущий шаг из `ROADMAP.md`, перечисли файлы, которые планируешь изменить, и зачем.
4. Если задача неоднозначна или потребует нового слоя/зависимости — сначала спроси пользователя.

## Строгие ограничения
- **Один шаг дорожной карты за раз.** Не начинай следующий без явного подтверждения владельца.
- Небольшой diff: не делай попутных рефакторингов, переименований и изменений форматирования.
- Не добавляй пакеты, библиотеки, DI-контейнеры, coordinators, repositories, use cases и дополнительные архитектурные уровни.
- Сохраняй SwiftPM, SwiftUI, MVVM-lite и текущие файлы. Создавай новый Swift-файл только если существующие файлы объективно не подходят; объясни причину.
- Не меняй `Package.swift`, минимальную версию macOS, build-скрипты и sandbox/entitlements без отдельного согласования.
- **Пока никаких тестов**: не добавляй test target, XCTest, CI, мок-систему и тестовые файлы. Позже вернёмся к этому осознанно.
- Не трогай пользовательские исходники, `.git`, `node_modules`, Android SDK, AVD, симуляторы, `ios/Pods` и другие данные ради «очистки» без отдельной утверждённой политики.
- Не включай автоматическую очистку при запуске/сканировании. Все операции удаления требуют явного действия и подтверждения пользователя.
- Не выполняй реальные команды удаления на машине пользователя без его прямого разрешения.
- Не используй `rm -rf`, оболочку `sh -c`, `bash -c` или интерполяцию непроверенных путей в команды удаления.
- `canClean`/UI-кнопка **не являются** проверкой безопасности. Проверки целевого пути, симлинков, типа файла и allowlist должны находиться внутри `CleanupService`.
- Внешние процессы (`du`) запускай с `Process.executableURL` и массивом `arguments`; обрабатывай ошибки, права доступа и ненулевой exit code.
- Не запускай тяжёлые файловые операции на main actor; SwiftUI-состояние обновляй на main actor.
- Не выдавай «успешно очищено», пока операция не закончилась; показывай частичные ошибки.
- Для Gradle не обещай, что очистка безвредна: зависимости могут скачиваться заново, активные сборки могут пострадать.
- `iOS Simulators`, `.android` и Android SDK на данном этапе **только анализ**.

## Как оформлять каждую законченную работу
Ответ агента всегда должен содержать:
1. **Что сделано** — 2–5 конкретных предложений.
2. **Какие файлы изменены** и за что отвечает каждое изменение.
3. **Как работает** — путь данных/события от View до сервиса.
4. **Что нового в Swift** — коротко и с параллелью к React/TypeScript, если полезно.
5. **Проверка** — фактически выполненная команда и результат; если сборка не запускалась, прямо так и скажи.
6. **Как проверить вручную** — короткие шаги в DevCleaner.
7. **Риски/ограничения** — без замалчивания.
8. **Что предлагается дальше** — но не выполняй следующий шаг автоматически.

После выполнения шага обновляй `ROADMAP.md` **только в части действительно завершённой работы**; не отмечай пункт сделанным, если не проверил результат. Если меняются обязанности файлов или поток данных — точечно обновляй `ARCHITECTURE.md`.

## Правила взаимодействия
- Объясняй изменения на русском; идентификаторы в коде — на английском.
- Не заменяй целые файлы без необходимости: предпочтительны небольшие изменения.
- Не стирай локальные правки пользователя.
- При обнаружении несоответствия документации и кода сначала объясни его, затем предложи минимальное исправление.
- Работа считается принятой **только после review владельца**.
